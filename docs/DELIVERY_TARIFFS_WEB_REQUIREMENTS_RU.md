# Тарифы доставки POS → база данных → сайт

Дата: 14 октября 2026 года. Статус: требования реализованы в рабочих копиях POS, Android Web и backend; публикация, Android CI и физическая приёмка ещё не выполнены. Подробности включения и ограничения: [DELIVERY_TARIFFS_IMPLEMENTATION_RU.md](DELIVERY_TARIFFS_IMPLEMENTATION_RU.md).

## Цель

Варианты из настроек «Стоимость доставки» на планшете должны сохраняться в базе backend. При оформлении заказа на сайте покупатель выбирает один из этих тарифов, видит его стоимость и итог с доставкой. Заказ поступает на планшет с выбранным тарифом и той же суммой.

Пример: в POS настроены «По городу — 5,00 BYN» и «За город — 10,00 BYN». При товарах на 30,00 BYN выбор «По городу» даёт итог 35,00 BYN на сайте, в базе и в полученном POS заказе.

## Исходное состояние

Проверены Android Web commit `2f421000e46b31c898c1cabb7d021413d88e2d57` и backend commit `893f3c42ca18a111929b1fe10b108322173f03d1`. В `web-source-manifest.json` указан авторитетный iPad source commit `57b3dbfc2233b4ac7536f5ad2943ce4806a79150`.

- POS хранит `state.deliveryRates` как список `{id, name, amount}` в существующем локальном ключе `prilavok_deliveryRates`. Создание, изменение и удаление находятся в `app/src/main/assets/pos/pos.html`.
- Выбор в `Web/js/features/cart-presentation.js` сейчас определяется суммой, а не ID. Два тарифа с одинаковой стоимостью нельзя надёжно различить в заказе.
- `Web/js/features/payment.js` проверяет наличие выбранной суммы в текущем списке тарифов. Стоимость добавляется в итог; при оплате положительная доставка создаёт существующее кассовое списание.
- При принятии веб-заказа `Web/js/features/web-orders.js` переносит `delivery_fee`, но устанавливает `deliveryTariffSelected: false`.
- Сайт `M-Pos-Backend/public/index.html` не предлагает список тарифов и показывает «Стоимость доставки будет рассчитана администратором».
- Backend использует общий `DELIVERY_FEE`; `checkout-service.js` сохраняет подготовленный заказ в `checkout_sessions.order_payload`, а SQL-функция `finalize_verified_checkout` создаёт заказ после подтверждения телефона. В `orders` есть `delivery_fee`, но нет отдельного справочника тарифов и снимка выбранного названия/ID.
- Текущая база — нативный PostgreSQL. Новые миграции относятся к `M-Pos-Backend/db/migrations`, а не к историческим миграциям Supabase.

## Обязательное поведение

### Настройка и синхронизация на планшете

1. POS остаётся источником списка тарифов. Добавление, переименование, изменение суммы и удаление выполняются в существующих настройках с действующими ограничениями доступа.
2. Локальное сохранение не отправляет данные в backend. Полный текущий список публикуется только кнопкой «Синхронизация с бэкендом» в сетевых настройках, после синхронизации каталога.
3. При ошибке сети пользователь видит отдельный статус тарифов и повторяет общую синхронизацию вручную. Старт, возврат на экран, восстановление сети и SSE ничего не публикуют. Старые автоматические очереди из backup не отправляются. Изменения во время отправки требуют следующего нажатия.
4. Первая публикация переносит уже существующие тарифы с их ID. Редактирование сохраняет ID; новый тариф получает новый ID, даже если название и цена совпадают с удалённым.
5. Backend применяет полный список атомарно. Отсутствующие в принятом списке тарифы становятся неактивными для новых заказов. Пустой список означает отключение доставки на сайте; отсутствие поля тарифов в запросе старого клиента ничего не удаляет.
6. Повтор одной публикации безопасен. Устаревший запрос не должен перезаписывать более свежий список. Нужны версия состояния и проверка порядка публикаций; восстановление резервной копии или сброс локальной версии не должны обходить эту проверку.
7. Справочник принадлежит заведению и назначенному POS-источнику. Backend проверяет право устройства менять тарифы; наличие произвольного `deviceKey` не даёт такого права. Другое устройство не заменяет список молча.
8. Название непустое, сумма конечная и неотрицательная, точность — до двух знаков после запятой. ID в списке уникальны; недопустимые значения и повторяющиеся ID отклоняют всю публикацию. Тариф 0,00 BYN разрешён.

### Выбор на сайте

1. При способе получения «Доставка» отображаются действующие тарифы: название и стоимость в BYN. Покупатель явно выбирает один вариант; первая строка не выбирается незаметно.
2. До выбора тарифа оформление доставки недоступно; интерфейс объясняет «Выберите тариф доставки». Адрес остаётся обязательным.
3. Итог отображает стоимость товаров, выбранную доставку отдельной строкой и общую сумму. Бесплатный тариф отображается как 0,00 BYN и считается полноценным выбором.
4. При переключении на самовывоз доставка равна нулю и не сохраняется в заказе. Возврат к доставке требует явного выбора тарифа.
5. Если тарифов нет, доставка недоступна с понятным объяснением; самовывоз работает. Ошибка загрузки списка не превращается в бесплатную доставку и не включает запасной общий тариф.
6. Сайт обновляет список при открытии оформления и перед созданием checkout. Если выбранный тариф удалён либо изменились его название/стоимость, показывает актуальные данные и просит повторно подтвердить выбор. Цена не меняется незаметно.
7. Тариф выбирается по ID. Одинаковая стоимость или одинаковое название не объединяют разные варианты.
8. Названия отображаются как текст с экранированием. Выбор доступен с клавиатуры и на мобильном экране; ошибки видны рядом с выбором доставки.

### Серверная проверка и создание заказа

1. Клиент передаёт ID выбранного тарифа и версию/ожидаемую стоимость для обнаружения устаревшего выбора. Backend самостоятельно читает активный тариф и рассчитывает итог. Переданные клиентом `deliveryFee` и `total` не являются источником цены.
2. Доставка без тарифа, неизвестный или неактивный ID и устаревший выбор отклоняются с понятной ошибкой. Checkout и подтверждённый заказ в этих случаях не создаются.
3. Для самовывоза сервер устанавливает стоимость доставки 0 и отсутствие тарифа независимо от присланных полей. Проверка способа получения должна исключать обход доставки нестандартным значением.
4. Денежные вычисления используют точные значения: целые копейки или PostgreSQL `numeric` с согласованным округлением. Доставка не должна начисляться дважды или поглощаться скидкой/подарком на товары.
5. При успешном создании checkout сервер фиксирует снимок: ID, название, стоимость и версию тарифа. Покупателю возвращаются серверные суммы для проверки перед переходом в Telegram.
6. Предлагаемое правило первой версии: снимок действует в пределах существующего срока checkout — 5 минут. Изменение или удаление тарифа после создания checkout не меняет его цену; новый checkout использует только актуальный список. После истечения срока требуется новое оформление. Это явно выбранное правило, которое нужно сохранить в интерфейсе и тестах.
7. Подтверждение телефона, создание заказа и резервирование товаров сохраняют текущую атомарность. `finalize_verified_checkout` переносит снимок тарифа из подготовленного checkout; не принимает новую стоимость из браузера или бота.
8. Повторное подтверждение не создаёт второй заказ и не начисляет доставку повторно. Ошибка или откат транзакции не оставляет частично созданный заказ.
9. В подтверждённом заказе сохраняются ID, название на момент оформления и `delivery_fee`. История не меняется при последующем переименовании, удалении или изменении цены тарифа.
10. Общий `DELIVERY_FEE` перестаёт определять новые заказы доставки после включения функциональности. Отсутствующий список не должен включать этот fallback.

### Получение и оплата на POS

1. В карточке веб-заказа, отложенном заказе и после восстановления сессии отображаются выбранное название и зафиксированная стоимость.
2. Принятие веб-заказа не требует повторного выбора местного тарифа. Корректный серверный снимок считается выбранной доставкой, включая 0,00 BYN.
3. Удаление или изменение локального тарифа после оформления не блокирует оплату подтверждённого веб-заказа и не пересчитывает его стоимость. Для локальных новых заказов сохраняется проверка действующих тарифов.
4. Выбор хранится по ID и снимку; сравнение только по сумме недопустимо. Поля должны переживать отложенный заказ, перезапуск и экспорт/импорт резервной копии.
5. Стоимость входит в чек и итог ровно один раз. Существующие правила кассового списания доставки сохраняются; новую кассовую проводку поверх текущей не добавлять.
6. Старые веб-заказы без снимка остаются доступными и сохраняют записанную сумму. Нельзя придумывать для них ID по совпадению цены; их прежнее поведение и ограничения нужно явно отделить от нового контракта.

## Предлагаемая модель и API

Это проект контракта, а не уже существующие таблицы и маршруты. Окончательные имена уточняются при реализации без изменения описанного поведения.

| Объект | Данные / назначение |
| --- | --- |
| Справочник `delivery_tariffs` | ID тарифа из POS, принадлежность заведению/источнику, название, точная сумма, порядок, активность, версия публикации, даты изменения |
| Состояние публикации | Назначенный источник, серверная версия и данные для безопасного повторения/отклонения устаревших запросов |
| Checkout | Снимок ID/названия/стоимости/версии внутри `order_payload` и серверные итоговые суммы |
| Подтверждённый заказ | ID тарифа и название на момент оформления; существующий `delivery_fee` хранит зафиксированную сумму |
| POS-сессия и отложенный заказ | Совместимые дополнительные поля ID и названия/снимка без потери существующего JSON |

- `PUT /api/device/delivery-tariffs`: авторизованная публикация полного списка и версии; ответ подтверждает применённую серверную версию. Конкретную защиту порядка и смены источника спроектировать до реализации очереди.
- `GET /api/delivery-tariffs`: публичный список активных тарифов с ID, названием, стоимостью, порядком и версией, без device key и иных внутренних данных. Чтение не допускает изменения справочника.
- `POST /api/checkout`: дополнительный `deliveryTariffId` и ожидаемая версия/стоимость для доставки; в ответе серверные стоимость доставки и итог.
- Существующие ответы заказов дополняются снимком тарифа, чтобы POS не искал его по цене в локальных настройках.
- Предлагаемые коды ошибок: `DELIVERY_TARIFF_REQUIRED`, `DELIVERY_TARIFF_UNAVAILABLE`, `DELIVERY_TARIFF_CHANGED`, `DELIVERY_SYNC_CONFLICT`. Ошибка конфликта не означает успешную публикацию; окончательные HTTP-статусы и формат согласовать с текущими API.

## Совместимость и границы

- Реализация затрагивает Android Web/POS, backend, PostgreSQL и гостевой сайт. Бот сохраняет сценарий подтверждения телефона; пересчёт тарифов в Telegram не добавляется.
- Общий POS JavaScript/HTML меняется в авторитетном iPad-источнике, затем переносится через `scripts/sync-pos-assets.py` с обновлением manifest. Отдельная копия денежной логики в Kotlin не создаётся. Репозиторий нативной миграции `M-POS-Android` не входит в эту задачу.
- Существующие ключи `prilavok_` и формат резервных копий сохраняются; дополнительные поля читаются обратно совместимо. Служебное состояние очереди не должно нарушать исходный формат данных.
- Новый справочник и поля добавляются отдельной миграцией PostgreSQL. Исторические заказы и существующая baseline-миграция не переписываются.
- Сначала устанавливаются совместимая миграция и backend, затем обновляется POS и публикуются тарифы. Новый выбор на сайте включается только после успешной первой публикации; до переключения действует прежний сценарий сайта. После переключения старые клиенты без ID не могут создавать новую доставку по общему `DELIVERY_FEE`; самовывоз остаётся совместимым.
- Автоматический выбор района по адресу, расчёт расстояния, геокодирование, бесплатная доставка от суммы заказа, расписания и управление курьерами в первую версию не входят. Пользователь выбирает подходящий вариант сам.

## Приёмка

| Сценарий | Ожидаемый результат |
| --- | --- |
| Первая публикация существующего списка | ID, названия и суммы совпадают в POS, PostgreSQL и на сайте |
| Создание, изменение, удаление и пустой список | Изменения видны после публикации; пустой список отключает только доставку |
| Ошибка локальной записи / отсутствие сети | Несохранённое не отправлено; сохранённое доступно offline, очередь повторяется без потери последнего состояния |
| Повтор, старый запрос, восстановление backup | Нет дубликатов или отката свежего списка; конфликт явно виден |
| Постороннее устройство / публичный запрос записи | Справочник не изменяется |
| Тарифы с одинаковой ценой / бесплатный тариф | Выбор различается по ID; 0,00 BYN разрешён при явном выборе |
| Товары 30,00 + доставка 5,00 | Сайт, checkout, база, POS и чек показывают 35,00 BYN |
| Подмена суммы, ID, типа получения | Сервер не принимает цену клиента и не позволяет обход правил доставки |
| Изменение тарифа до создания checkout | Покупатель видит обновление и повторно подтверждает выбор |
| Изменение/удаление после создания checkout | В пределах 5 минут сохраняется снимок; новый checkout использует актуальные тарифы |
| Подтверждение, повтор и истечение checkout | Один заказ/резерв, неизменный тариф; просроченное оформление не создаёт заказ |
| Переключение доставка → самовывоз → доставка | На самовывозе ноль; при возврате нужен выбор |
| Нет тарифов / ошибка загрузки | Нет скрытого бесплатного или запасного тарифа; самовывоз работает |
| Принятие WEB-заказа, отложенный заказ, перезапуск | Выбор и сумма сохранены, повторного выбора нет; кассовое списание выполняется один раз |
| Старый заказ / резервная копия / скидки и loyalty | Суммы истории и данные сохранены; доставка не теряется и не дублируется |

При реализации нужны проверки backend/SQL атомарности и денежных расчётов, регрессии сайта и POS, source parity и CI Android. Физическая приёмка включает изменение тарифа offline, восстановление сети, реальный заказ через сайт/Telegram, получение на планшете и оплату с проверкой чека и кассового движения.

Первый этап включал исследование и описание требований. На следующем этапе по поручению пользователя добавлены код, миграция PostgreSQL и регрессионные проверки. Выполненные проверки и оставшаяся приёмка перечислены в документе реализации; первоначальное описание требований сохраняется как контракт.
