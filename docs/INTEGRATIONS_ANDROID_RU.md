## Найденные дефекты

1. «Тест заказа» отправлял POST /api/orders/test: такого маршрута в текущем backend нет. Реальное создание заказа требует подтверждения телефона и состава заказа; диагностический запрос не должен создавать продажу.
2. Telegram-тест читал только поля открытого окна настройки; с основного экрана они отсутствуют. Статус показывался в элементе под модальным окном, а подтверждение native callback не имело requestId и общего тайм-аута.
3. Отправка operational snapshot считала любой HTTP 200 успехом. Backend возвращает HTTP 200 также с applied=false, ignoredAsStale=true. База принимает только возрастающий snapshot_revision: новый APK/импорт с тем же deviceKey и меньшим локальным счётчиком мог молча потерять переключение. Это подтверждённый дефект обработки протокола; без авторизованного ответа планшета нельзя утверждать, что именно он вызвал наблюдаемый сбой.
4. После сетевого сбоя outbox получал nextAttemptAt, но отсутствовал таймер следующей попытки в активном приложении.

## Изменения Android Web

Внешний android-integrations.js загружается после исходных feature modules перед loadAll. Финансовая логика, продажи, склад и схема резервных копий не меняются.

- Backend-тест сохраняет настройки перед сетевым эффектом, проверяет health и авторизованный /api/operational/state, затем перезапускает основной SSE с сохранёнными настройками. HTTP 401/403 отделены от timeout и отсутствующего маршрута.
- Кнопка «Проверить канал заказов» использует авторизованный state и короткое отдельное SSE-соединение /api/orders/events. Оно закрывается после onopen/error/10 секунд и не принимает, не сохраняет, не создаёт заказы; основной поток остаётся открытым.
- Telegram-тест берёт введённые поля в открытом окне, иначе сохранённые настройки. Пустое введённое поле не подменяется старым значением. MainActivity подключает уже существующий correlated onTestResult callback TelegramClient; повторный тап не дублирует запрос. Виден progress/result в основном экране и модальном окне; общий timeout 35 секунд, поздний callback игнорируется.
- Для новых demand snapshots монотонная ревизия не меньше текущего времени в миллисекундах. Старые сохранённые outbox со счётчиком ниже 10^12 также обновляются перед отправкой, сохраняя их demand payload. Revision и outbox сохраняются перед POST.
- Только ok=true, applied=true и отсутствие ignoredAsStale подтверждают отправку. Отказ сохраняет outbox и видимую причину; retry использует исходный bounded backoff до 60 секунд. Работа приостанавливается в фоне; текущий operationalController отменяется при visibilitychange. Unsaved URL из окна настройки не используется для operational отправки.
- Нет автоматической синхронизации каталога, изменения заказов или переноса токенов в Git. Backend/project_bot/Supabase schema не изменены.

Приложение отправляет Telegram-тест и отчёты непосредственно в Telegram Bot API с token/chat/topic из настроек. Получение заказов идёт по backend SSE; сценарий подтверждения телефона в project_bot — отдельный канал. Успех SSE не подтверждает Telegram-доставку.

На новом APK:

1. Backend-тест: получить «ключ устройства принят». Ошибка 401/403 требует проверки зарегистрированного deviceKey; не генерировать другой ключ вслепую. Telegram-тест: результат виден, при успехе тестовое сообщение появляется в правильной группе/теме.
2. Проверка канала: успех без фиктивного заказа, затем реальный заказ приходит как раньше.

4. Повторить offline/online: последнее состояние сохраняется и передаётся после восстановления связи; быстрые переключения оставляют последнюю выбранную загрузку.

При stale revision проверить дату планшета; конфликт с ещё большей серверной ревизией требует отдельной диагностики, а не ложного сообщения об успехе.
