## Что исправлено в выбранной области

1. **Общий барьер.** Все обращения через PrilavokCore.Storage.set/remove и saveKey проверяют committing, recovery, criticalOperationBusy, storageBroken и незавершённый журнал. Записать/удалить сам journal через обычный API нельзя. Временный отказ из-за занятости не объявляется повреждением хранилища. После реальной ошибки записи финансовый отказ сохраняется.
2. **Одна локальная операция.** Android использует синхронный localStorage, поэтому запись журнала, его ключей и очистка выполняются в одном JS turn без await между ключами. Другие browser callbacks не вклиниваются между этими шагами. Финансовые source handlers по-прежнему ожидают Promise и публикуют state после commit; criticalOperationBusy защищает и эту публикацию. При отказе запись не откатывается автоматически: journal roll-forward остаётся в существующем формате v1 и проигрывается на запуске. Recovery проверяет весь набор ключей до первой записи.
3. **Обычные связанные изменения.** Синхронные handlers корзины, категорий/раскладки, inventory draft/config, hall/bookings и основных настроек собирают свои saveKey в одну запись журнала. Сохраняется прежний синхронный return, включая boolean startInventory/saveNetworkSettings. Пока source handler собирает кандидата, render/close/flash и внешние эффекты откладываются. После commit выполняются; при ошибке изменённые поля state восстанавливаются, успех/закрытие формы подавляются. Контекст не распространяется через await. Снимки ограничены полями области, а не копией всех продаж при каждом клике корзины. Demand и outbox строятся до commit, HTTP flush после него.
4. **Асинхронные пути.** Редакторы, справочники, импорт каталога, приёмка и WEB действия проверяют барьер до входа, а Storage проверяет его снова непосредственно при записи после await. Их исходные snapshot-before-write/await-before-state правила сохранены. Импорт backup имеет исключительную lease до завершения обновления state; второй импорт/финансовая запись блокируются, render откладывается. Это не закрытие фото-cleanup дефекта R08.

saveKey и сохранение текущей сессии теперь возвращают подтверждение или бросают ошибку вместо подавления отказа в рабочем режиме. Исключение — загрузка повреждённого хранилища: compatibility defaults не записываются, возвращается false; запуск может завершиться в read-only режиме с предупреждением. В частности, ready handler больше не может считать отказ session.write успешным, но вся recovery-логика ready (R13) требует отдельного этапа.

## Совместимость и ограничения

- Ключи prilavok_, формат данных, backup v13, журнал v1, деньги/рецептуры/наличие и очередность внешних бизнес-триггеров сохранены. Нативный проект, сайт и бот не менялись. Сертификат/package/version pipeline не менялись.
- Дополнительные журналы обычных изменений требуют свободного места. Проблема роста истории/quota (R17) остаётся.
- После частичной записи UI сохраняет прежний снимок до restart, но журнал завершит предложенные изменения. Сообщение объясняет необходимость восстановления; повтор запрещён. Это roll-forward, не обещание отката выполненной записи на диске.
- Отдельные legacy ключи принтеров/звука в network-printer.js используют собственный localStorage напрямую и не входят в финансовые documents. Их совместное восстановление с backup относится к R08; полный контроль этих ключей этим этапом не заявляется.
- Низкоуровневые async callback могут изменять свой status в памяти до попытки записи. При конфликте они не перезаписывают финансовые документы и не начинают HTTP до initial persist; полноценная очередь и in-flight/retry политика loyalty — R12, Telegram — R15.
- Пересчёт склада, подарки со скидками, инвентаризация, рецептуры активного заказа и внешнее подтверждение денег остаются отдельными открытыми рисками. Устранение R01 не является заявлением о полной безопасности.

## Регрессии и проверки

Переработана прежняя проверка конкурирующего journal под синхронную Android запись; добавлены **13 сценариев** в tests/source-product-stock.test.cjs на фактических source handlers:

- отказ обычной записи/изменения корзины во время публикации финансовой операции без ложного storageBroken;
- защита journal от прямого overwrite/remove и async editor при recoveryPending;
- rollback кандидатной корзины/подавление render при session failure, затем идемпотентный roll-forward;
- общий journal удаления hallTables/bookings, ошибка второго ключа, восстановление обоих;
- отказ network settings с false без тестового HTTP и сообщения об успехе;
- сохранение синхронного boolean startInventory;
- demand+outbox сохранены до внешнего flush;
- валидация всего recovery journal до первой business write;
- отказ фонового loyalty initial persist до HTTP при финансовом busy;
- exclusive backup lease до async публикации state и запрет второго import/оплаты;
- один журнал переименования категории для products/navigation/layout и recovery после отказа второго ключа;
- ошибка deferred render не откатывает уже сохранённую корзину и не выдаётся за отказ записи;
- read-only startup не заменяет повреждённые документы совместимыми значениями по умолчанию.

**Локально выполнены только node --check изменённых JS и git diff --check.** Тесты, lint и APK не запускались согласно AGENTS.md §8; результат ожидается в Actions. На планшете не проверено. Существующие financial/source-parity regression остаются и должны выполняться в CI вместе с новыми.

## Приёмка на тестовой установке

1. Обычная корзина/park/pay/return и перезапуск: один чек и одно списание.
2. Категория, table+booking, настройки и inventory draft: после restart все связанные поля согласованы.
3. Inject failure journal/key/clear только на тестовой установке: успех не показан, новая запись не принимается, restart завершает все ключи ровно один раз.
4. Loyalty ответ/reconnect и WEB event во время финансовой записи не заменяют свежий чек старым orders/parked.
5. Импорт v13 с открытым заказом/подтверждённой split частью: без второго импорта/конкурентной оплаты и с последующей сверкой данных.
