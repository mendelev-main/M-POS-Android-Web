# Рабочий цикл

1. **Ориентация.** Прочитать корневые инструкции и harness. Сохранить чужие изменения; выбрать существующий checkout. Выполнить статический preflight. Ошибку происхождения runtime устранить до функциональной правки.
2. **Объём.** Сформулировать ожидаемое поведение и критерии приёмки. Для UI указать нужные размеры и реальный сценарий. Для сложной задачи вести небольшой план в `harness/tasks/<slug>.md`; для простой достаточно записи журнала. Уже согласованные действия не требуют повторного подтверждения.
3. **Реализация.** Менять слой-владелец. Общий web runtime: commit в upstream, затем штатный sync в Android. Прямой патч сгенерированных файлов не заменяет исправление источника. Сохранить offline-first, persist-before-network и схемы backup.
4. **Проверка.** Добавлять содержательные регрессионные тесты для логики; UI проверять на синтетических данных в полном runtime. Для планшета использовать минимум 1024×768 и 1280×800, когда это относится к изменению. Не выдавать браузерный предпросмотр за проверку физического устройства.
5. **CI.** GitHub Actions запускает preflight, самопроверки harness, JS-набор, JVM и lint. Подписанная сборка зависит от успешных проверок. Статусы queued/in_progress/pending не равны success. Локальные тесты и сборка — только по отдельному прямому указанию пользователя.
6. **Доставка.** Если требуется APK, дождаться успешного workflow, проверить commit, checksum, identity, постоянный сертификат и нужные встроенные файлы. Зафиксировать результаты в журнале. Отдельно перечислить физические проверки, которые ещё не выполнены.

## Запись журнала

Дата и задача; объём; существенные решения; исходный commit; выполненные команды и CI URL; результат; непройденные проверки и следующий необходимый шаг. Не копировать пароли, токены, содержимое заказов или персональные данные. Не отмечать задачу завершённой по одному наличию кода. Позднее полученные результаты дописывать явно.
